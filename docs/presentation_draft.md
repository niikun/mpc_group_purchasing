## スライド2 — 問題設定:共同購入のジレンマ

**載せる要素**
- 例:外食チェーン各社が塩・砂糖・食用油をまとめて仕入れて単価を下げたい
- でも各社の発注量・希望価格は競争機密 → 互いにも運営者にも渡したくない
- 「隠したまま協調する」

**原稿**

たとえば外食チェーン数社が、塩や砂糖、食用油といったコモディティ資材を共同で仕入れれば、量がまとまるので単価を下げられます。ところが、各社がどれだけ発注したいか、いくらまでなら出すか、というのは競争上の機密です。相手にも知られたくないし、束ねる運営者にも預けたくない。

普通なら「信頼できる第三者にみんなのデータを渡して集計してもらう」ところですが、その第三者が単一障害点になり、談合の温床にもなります。そこを暗号でなくしたい、というのがこのプロジェクトです。「入力は隠したまま、協調の結果だけ出す」。

## スライド3 — コア機構:ダブルオークション

**載せる要素**
- 価格グリッド `[95, 100, 105, 110, 115, 120, 125, 130, 135]`(9段)
- 買い手:上限価格を非公開入力 / 売り手:下限価格を非公開入力
- 各価格帯の需要合計 D(p)・供給合計 S(p) だけを合算
- 清算価格 = `D(p) ≤ S(p)` を満たす最も低い価格(買い手優先)
- 公開されるのは D(p)/S(p)・清算価格・成立総量。個社の入力は最後まで非公開

**原稿**

仕組みはダブルオークションです。価格はあらかじめ9段のグリッドに固定してあります。買い手は「この価格までなら買う」という上限を、売り手は「この価格を下回っては売らない」という下限を、それぞれ非公開で入れます。

そこから、価格帯ごとに需要の合計 D(p) と供給の合計 S(p) を作ります。個社の数字は足し込まれるので出てきません。そして需要と供給が交わる価格 —— 正確には「需要が供給以下になる最も低い価格」——を清算価格として、そこだけ復元します。成立数量は清算価格時点の需要・供給から比例配分します。

最終的に外に出るのは、需要曲線・供給曲線・清算価格・成立総量、それと各社に個別に返す約定量だけ。誰がいくらで何個欲しかったかは分かりません。

## スライド4 — 2段階構成と発表の主眼

**載せる要素**
- 第1段階:MPC(加法的秘密分散、3ノード)/ Rust / 完了
- 第2段階:FHE(Zama `tfhe-rs`)/ Rust / コア完了
- **同じロジックを2つの技術で書いて、信頼の起点・計算コスト・スケールを比較するのが主眼**
- 上乗せ①:LLM 入札エージェントの多ラウンド観察
- 上乗せ②:エージェント入力の出所を ZK(SP1)で証明する PoC

**原稿**

実装は2段階です。第1段階が MPC、複数のノードで秘密分散して協調計算する方式。第2段階が FHE、暗号文のまま計算する完全準同型暗号で、Zama の tfhe-rs を使いました。両方 Rust です。

大事なのは、この2つで**まったく同じダブルオークションのロジック**を書いたことです。そうすると、信頼をどこに置くか、どれくらい重いか、参加者が増えたときどうなるか、といった軸で正面から比較できます。それがこの発表の主眼です。

上乗せは2つあります。ひとつは、入札の判断を LLM にやらせて何ラウンドも回すとどうなるか、という観察実験。もうひとつは、その LLM への入力が本当に自社データだけだったことを、ZK で証明できないか試した PoC です。この2つを最後に少し話します。

## スライド5 — 第1段階 MPC のしくみ

**載せる要素**
- 加法的秘密分散:秘密 `x` を `x = s1 + s2 + s3 (mod M)` に3分割、各ノードに1つずつ
- 2つ以下のシェアからは何も分からない / 3つ揃えて初めて復元
- 各社が価格帯ベクトルを分割 → ノードは受け取ったシェアを**足すだけ** → 3ノード分を合わせて D(p)/S(p) を復元
- 清算価格・按分は復元後の平文で計算

**原稿**

第1段階の秘密分散は、いちばん素朴な加法的分散です。秘密の値 x を、乱数を使って足すと x に戻る3つの数に分けて、3つのノードに1つずつ配ります。2つまでなら手に入れても、残り1つが分からない限り元の値は完全に分かりません。3つ揃って初めて復元できます。

各社は、自分の価格帯ごとの希望数量ベクトルをこの方式で3分割して送ります。ノード側は、受け取ったシェアをただ足し込むだけ。最後に3ノードのぶんを合わせると、各社の生の値は出てこないまま、合計の需要曲線と供給曲線だけが復元されます。清算価格の探索と按分は、その復元後の平文に対して普通に計算します。

## スライド6 — MPC 実装:実プロセス版の流れ

**載せる要素**
- `participant`(各社)× 5 が1社分だけシェアを作って3ノードに送る
- `node` × 3(別プロセス、TCP + tokio)がシェアを集計
- `coordinator` が3ノードから結果を集めて `add_node` → `clearing_price`(公開データのみ)
- 個別の按分は各社自身の役目に分離(1社分のデータしか触らない設計)
- 固定シナリオ:買い手3・売り手2 → 清算価格 110

**原稿**

実装は、1プロセス内のシミュレーションから始めて、最終的に本当にプロセスを分けました。各社にあたる participant が5個、それぞれ自分1社分のシェアだけを作って、3つの node プロセスに TCP で送ります。node はシェアを積み上げるだけ。coordinator が3ノードから集計結果を集めて復元し、清算価格までの「公開してよいデータ」だけを計算します。

按分の計算は coordinator から外して、各社自身の仕事にしました。こうすると、どのコンポーネントも一度に1社分のデータしか触りません。これは後で話す LLM エージェントの「1回の呼び出しは1社分」という要件の土台にもなっています。

固定シナリオ、買い手3社・売り手2社で回すと、清算価格 110 が出ます。

## スライド7 — 第2段階 FHE のしくみ

**載せる要素**
- `client_key` で暗号化 / `server_key`(公開評価鍵)で暗号文のまま演算 / 復号は `client_key` のみ
- 型で信頼モデルが強制される(`decrypt` は `&ClientKey` しか受け取らない)
- 同じ4フェーズ:derive → 集計 → 清算価格 → 按分。すべて暗号文のまま
- 型は `FheUint16`(価格・合計が収まる)、按分の乗除で `FheUint32`

**原稿**

第2段階の FHE は、秘密鍵 client_key で暗号化して、公開の評価鍵 server_key を使って暗号文のまま計算し、復号は秘密鍵を持つ人だけができる、という構造です。tfhe-rs だと、復号のメソッドが秘密鍵の参照しか受け取らないので、信頼モデルが型で強制されるのが面白いところでした。

やることは MPC と同じ4フェーズ、derive・集計・清算価格・按分です。違いは、全部を暗号文のまま、復号せずにやること。ビット幅がそのままコストなので、価格や合計が収まる16ビットを基本にして、掛け算・割り算の出る按分だけ32ビットに広げています。

## スライド8 — FHE 実装:分岐できない世界

**載せる要素**
- 暗号 bool(`FheBool`)は `if` の条件に使えない → 平文に戻す = 復号
- データ依存の分岐はすべて **cmux**(`cond.if_then_else(a, b)`)に置換
- derive:9価格帯すべてを無条件に評価して cmux で選ぶ
- 清算価格:`break` できない → 9バンド全評価 + 「見つけた」フラグの**ラッチ**(OR は単調増加)
- 按分:ゼロ除算も「計算してから cmux で捨てる」

**原稿**

FHE で本質的にしんどいのは、暗号のまま分岐できないことです。比較の結果は暗号化された bool になって、それを if の条件には使えません。使おうとすると復号することになって、秘密計算の意味がなくなる。

なので、データに依存する分岐は全部 cmux —— 暗号の bool で2つの値から選ぶ演算 —— に置き換えます。derive なら、9つの価格帯を全部無条件に評価して、参加する/しないを cmux で選ぶ。清算価格の探索は、MPC だと「安い方から見て最初に条件を満たしたら break」でしたが、FHE では break できないので、9バンド全部評価して、「もう見つけた」というフラグを OR で更新していく。OR は一度立つと戻らないので、ラッチとして使えます。按分のゼロ除算対策も、割り算は必ず実行して、結果を cmux で捨てる、という形になります。

つまり「早期終了できない」というのが、後の性能差にそのまま効いてきます。

## スライド9 — 定性比較

**載せる要素(表)**

| 軸 | MPC(3ノード加法分散) | FHE(tfhe-rs、単一評価者) |
|---|---|---|
| 信頼の起点 | 3ノードが全員結託しない限り秘匿(1人でも正直なら安全) | `client_key` を持つ者は全部復号できる。鍵配布は簡略化(未解決) |
| 早期終了 | できる(復元後の平文でループ、`break`) | できない(暗号値で分岐不可、全価格帯を必ず評価) |
| コストの出方 | ノード間の通信ラウンド。演算自体はほぼ無料 | 単一マシンの計算時間。当事者間通信はゼロ |
| 参加者数スケール | 集計はシェアの加算 ≈ 無料 | 集計 O(参加者) で非ゼロ、按分は1社ごとに秒級 |
| オンチェーン性 | 本質的にオフチェーン | 本実装はオフチェーン(fhEVM は採用せず) |
| 実装で当たる壁 | 分散システム(非同期・通信・ロバスト性) | 回路設計(ビット幅・cmux 化・鍵ライフサイクル) |

**原稿**

定性的な比較です。信頼の起点がまず違う。MPC は3ノードが全員で結託しない限り安全で、1人でも正直なら入力は守られます。FHE は、秘密鍵を持っている人は何でも復号できてしまうので、その鍵を誰がどう分散して持つか、という問題が残ります。今回はそこは簡略化しました。

早期終了はさっき言った通り。MPC はできて FHE はできない。

コストの出方も対照的で、MPC はほぼ通信レイテンシで、計算そのものはタダみたいなものです。FHE は逆に、計算中の通信はゼロだけど、演算そのものが重い。

実装して詰まるポイントも違って、MPC は分散システムの難しさ、非同期とか通信とかロックの話。FHE は回路設計の難しさ、ビット幅の予算管理とか、分岐を全部 cmux に潰す作業でした。

## スライド10 — 定量比較:µs 対 100 秒

**載せる要素**
- 固定シナリオ:買い手3 + 売り手2、清算価格 110
- 計測環境:i7-10850H(6C/12T)、WSL2、`--release`、FHE は `target-cpu=native`
- MPC:1取引 通し median **1.2 µs**(n=1000)
- FHE:1取引 通し median **105 秒**(n=4、先頭破棄)
  - 集計 16.6 s / 清算スキャン 12.6 s / 按分 ×5 = 75.8 s(≈15.2 s/社)
  - 鍵生成 818 ms・入力暗号化 5.1 ms(1回のみ、区間外)
- **比 ≈ 8.8 × 10⁷ 倍(約8桁)**

**原稿**

定量です。同じシナリオ、買い手3・売り手2で、1取引を通しで測りました。

MPC は中央値 1.2 マイクロ秒。1000回まわした中央値です。FHE は中央値 105 秒。5回まわして最初の1回を捨てた残りです。内訳は、集計が17秒弱、清算価格スキャンが13秒弱、按分が5社で76秒、按分だけで全体の7割です。鍵生成と入力の暗号化は1回きりなので区間の外に出しています。

比にすると、およそ8桁、9千万倍くらい違います。有効数字2桁で十分な差です。

## スライド11 — なぜ8桁も違うのか

**載せる要素**
- FHE 105s の内訳(通しに占める割合):按分 **72%**(75.8 s)/ 集計 **16%**(16.6 s)/ 清算スキャン **12%**(12.6 s)
- 演算コストの階層(このマシン):16bit 準同型加算 ≈ ms / 16bit 比較・cmux ≈ 10〜100 ms / **32bit 暗号÷暗号の除算 ≈ 秒**
- 按分 = `FheUint32` への拡張 + 暗号×暗号の乗算 + 暗号÷暗号の除算。1社あたり ≈15 s、5社で75.8 s
- 清算スキャンは早期終了できず9バンド全評価 → 価格グリッド段数ぶんの**固定費**(12.6 s)
- 集計は参加者数にほぼ線形(3社 9.4s≈3.1s/社 → 5社 16.6s≈3.3s/社)
- MPC は演算がローカルな法加算のみ = ほぼ0。通しの**1.2 µs という数字自体が**その証拠

**原稿**

なぜこんなに違うのか、実際の内訳で見ます。FHE の105秒のうち、按分が72%、集計が16%、清算スキャンが12%。7割が按分、しかも按分は「暗号を暗号で割る」割り算です。このマシンで測ると、16ビットの準同型加算はミリ秒、16ビットの比較や cmux は10〜100ミリ秒、それに対して32ビットの暗号÷暗号の除算は秒単位で、そこで1桁2桁変わります。按分が1社あたり約15秒、5社で75.8秒というのはここから来ています。

集計と清算スキャンにも理由があります。集計は参加者数にほぼ比例して伸びる —— 3社なら1社あたり3.1秒、5社なら3.3秒。清算スキャンは早期終了できないので、需要がゼロの価格帯も含めて9バンド全部を評価する固定費で、12.6秒。

MPC 側はこの逆で、必要な演算がローカルな法の足し算だけなので、通しで1.2マイクロ秒という数字そのものが「重い処理が存在しない」ことの証拠になっています。

一方で FHE は、計算中に当事者間の通信が一切いらない、という強みがあります。そこはトレードオフです。

## スライド12 — 上乗せ①:LLM 入札エージェント

**載せる要素**
- spec 11章:各社が「自社データのみ」を見て入札案を作り、**人間が確認してから確定**(RealPage 事件対策)

- 集計は本物の秘密分散パスを通す
- モデル `claude-haiku-4-5`、15ラウンド

**原稿**

最後に上乗せの話です。仕様の11章に、入札の判断を AI に手伝わせる機能を置いています。ただし完全自動化はしない。各社の AI は自社のデータしか見ないし、出てきた入札案は人間が確認してから確定します。これはアメリカの RealPage という、賃料設定アルゴリズムが事実上の価格カルテルになった事件を踏まえた設計です。

そこから派生させた研究モードとして、入札判断を LLM に任せて、人間確認を外して何ラウンドも自動で回すとどうなるか、を観察しました。1回のモデル呼び出しに渡すのは、その1社のプロフィールと、過去ラウンドの公開結果だけ。他社の数字は一切入れません。集計部分は本物の秘密分散を通しています。モデルは Haiku、15ラウンド回しました。

## スライド13 — 観察結果(15ラウンド)

**載せる要素**
- 図:threshold 推移 + participation(`analysis_demo.ipynb` の LLM セル)
- R7 で固定点に収束、8ラウンド維持(清算価格 120)
- b1(上限115):安く張るシェーディングを試して失敗 → 以後締め出し。ガードレールが檻に
- s2(下限105):下限を吊り上げ 125 まで → R5–6 は全社約定ゼロ(市場崩壊)→ 120 に撤退して収束
- 暗黙の協調は出ず(投げ売り役 s1 が追従しない)

**原稿**

結果です。まず、系全体が7ラウンド目で固定点に落ち着いて、そこから8ラウンドまったく同じ状態が続きます。

個別に見ると面白い動きがあって、上限115の買い手 b1 は、最初のうち「あえて安く張って様子を見る」シェーディングを試すんですが、清算価格が上がって自分だけ市場から外れる。以降は上限いっぱいの115に張り付くんですが、市場価格が120に上がってしまったので、残り全ラウンド一度も約定できません。人間が置いた「ここまでしか出すな」というガードレールが、価格上昇後は檻になった、という形です。

売り手の s2 は逆に強気で、下限を125まで吊り上げます。そのラウンドは買い手が誰もついてこられず、2ラウンド連続で市場全体が止まります。s2 自身の売上も消える。そこで s2 は120に引き下げて、以降は落ち着く。

談合的な協調は出ませんでした。もう一方の売り手 s1 が「在庫過多で量をさばきたい」投げ売り役なので、s2 が吊り上げても追従せず、s2 の高値は空振りに終わります。

## スライド14 — 手書きルール版との対比

**載せる要素(表)**

| | 手書きルール(8/21) | LLM(15ラウンド) |
|---|---|---|
| 適応 | `adjust` / `adjust_aggressive` を人間が固定 | モデルが毎回判断 |
| passive レジーム | 数ラウンドで収束 | 上限に余裕がある b2 が同じ挙動(初手から不動) |
| aggressive レジーム | ルールが強制し**永久に振動** | s2 が吊り上げ → 市場崩壊 → **自ら撤退して収束** |
| 追加で見えたこと | (埋め込み済み) | 限界的な立場の社が passive/aggressive を自発的に使い分け。強気は長期では自己制限的 |

**原稿**

8月に、同じ実験を手書きの適応ルールでやっていました。「成立したら何もしない」という控えめルールは数ラウンドで収束する、「成立しても条件を吊り上げ続ける」強気ルールは永久に振動する、という結果でした。

LLM 版で対比すると、控えめレジームは、上限に余裕のある買い手がそのまま再現します。強気レジームは、手書きだとルールが振動を強制するので絶対に収束しないんですが、LLM の売り手は「吊り上げすぎると自分の売上ごと消える」と気づいて撤退して、収束しました。つまり、判断するエージェントを入れると、強気な行動が長い目で見て自己制限的になる。市場での立ち位置に応じて、両方のレジームを勝手に使い分けていました。

## スライド15 — 上乗せ②:入力証明の ZK PoC

**載せる要素**
- 課題(spec 11.6 / 16章):「モデルへの入力が本当に自社データのみだった」ことの暗号学的証明はしていない
- ハッシュ照合だけでは閉じない:検証者に profile を明かさず、その profile に対する計算の正しさを示す必要がある
- 構成:各社が事前に `commitment = sha256(profile‖salt)` を公開 → SP1(zkVM)の guest が `profile`/`salt`/公開履歴を秘密の witness として受け取り、`commit_profile` と `render_prompt`(実パスと同じテンプレコード)を再計算 → `commitment` / `history_digest` / `prompt_hash` を journal(公開出力)にコミット
- 実測:`--execute` で再計算一致を確認、`--prove` で証明生成 → 検証まで通過(`proof verified`)
- 言えること:「送信プロンプトは、コミット済み profile と公開データだけの関数だった」を profile を明かさず示せる
- 言えないこと:モデルが実際にその入力だけから推論したこと(verifiable ML inference は非現実的)、学習データの素性、提案の妥当性

**原稿**

もう一つの上乗せです。仕様の11章にも書きましたが、「AI への入力が本当に自社データだけだった」ことの暗号学的な証明はしていませんでした。これをどこまで詰められるか、1週間で試しました。

ハッシュを取って比較するだけでは足りません。検証者に profile そのものを見せないと再計算できないので、それでは秘密を守るという目的と矛盾します。必要なのは、秘密を明かさずに、その秘密に対する計算が正しいことを示す仕組みです。

そこで、各社が事前にプロフィールのコミットメント——ハッシュに近いものです——を公開しておき、SP1 という zkVM の中で、そのプロフィールと公開結果だけからプロンプトを組み立てる、実際のコードと同じ関数を実行させます。zkVM は「秘密の入力からこの計算をして、この公開出力が出た」ということを証明します。実際に、コミットメントとプロンプトのハッシュを実行時に一致させ、証明を生成して検証まで通しました。

これで言えるのは、「送ったプロンプトは、事前にコミットした自社データと公開データだけの関数だった」ということです。言えないのは、モデルが本当にその入力だけから推論したかどうかや、学習データの素性です。そこは今の技術では暗号で閉じられません。

## スライド16 — 制限事項と主張しないこと

**載せる要素**
- 鍵管理の簡略化:MPC は 3-of-3(しきい値 k-of-n 未実装)、FHE はしきい値復号 KMS なし。「復号権限の分散」は未解決
- MPC は準正直モデル。悪意あるノードの改ざん耐性(能動的安全性)はない。証明も伴わない
- FHE の按分に参加ゲート未実装(不参加社の生出力が 0 にならない)
- LLM 観察は単一の確率的1実行。数量は制御していない(清算価格が狙いの105でなく115〜125に着地)
- 「モデルが本当に自社データだけで計算した」ことは暗号では閉じられない(意味的性質)
- ZK PoC:`prompt_hash` が実際に API へ送られた文字列と一致することの接続は未実装。テンプレコードも `mpc-rust` と guest で二重管理(本番化には単一の共有クレートへの統合が必要)

**原稿**

正直に制限を並べます。まず鍵の分散。MPC は3ノード全員が必要な 3-of-3 で、k-of-n のしきい値版は未実装。FHE は本来 Zama がしきい値復号の仕組みを持っているんですが、それは使っていません。「復号する権限を安全に分散する」という部分は、どちらも解けていません。

MPC は準正直モデルで、ノードが嘘の集計をしても検出できません。FHE も単一の評価者が誤った回路を回しても分かりません。証明は付いていない。

FHE の按分は、清算価格で参加していない社を除外するゲートが暗号側で未実装で、そこは既知の穴です。

LLM の観察は1回の確率的な実行なので、統計ではありません。それと、「AI が本当に自社のデータだけを見て判断したか」は、そもそも暗号で証明できる性質ではない、というのは仕様にも書いています。

ZK PoC にも穴があります。証明しているのは「プロンプトはコミット済みデータの関数だった」までで、そのハッシュが実際に API に送られた文字列と一致することの接続はまだ繋いでいません。テンプレのコードも、実パスと guest とで二重管理になっています。

## スライド17 — まとめ

**載せる要素**
- 同じダブルオークションを MPC と FHE で実装
- MPC:信頼を3ノードに分散、演算はほぼ無料(µs)、コストは通信ラウンド、早期終了できる
- FHE:当事者間通信ゼロ、暗号のまま分岐なしで全評価、1取引 ~100 秒、早期終了できない
- 差は約8桁。支配項は暗号除算を含む按分
- 上乗せ①:LLM 入札エージェントは15ラウンドで収束、強気な売り手も自ら撤退
- 上乗せ②:エージェント入力の出所を ZK(SP1)で証明する PoC が動作(証明生成・検証まで確認)

**原稿**

まとめます。同じダブルオークションを2つの技術で書いて比べました。MPC は信頼を3ノードに分散して、計算そのものはほぼタダ、コストは通信、早期終了できる。FHE は当事者間の通信がいらない代わりに、暗号のまま分岐なしで全部評価するので、1取引100秒、早期終了できない。差はおよそ8桁で、支配項は暗号の割り算を含む按分でした。

上乗せは2つ。LLM 実験では、入札判断をエージェントに任せても15ラウンドで収束して、強気な売り手も市場を壊したあと自分で引き下がる、という挙動が見えました。もう一つ、その入力が自社データだけだったことを ZK で証明する PoC も、証明生成から検証まで実際に動くところまで確認しました。

以上です。

## 想定質疑メモ

- **なぜ fhEVM(オンチェーン)にしなかったか** — 残りコース期間で Solidity + TypeScript を新規に学ぶコストと、Rust の知識をそのまま活かせる tfhe-rs を天秤にかけて後者。トレードオフとしてオンチェーン検証としきい値復号 KMS は諦めた。
- **FHE 100秒は実用にならないのでは** — バッチ決済(1日1回など)なら許容範囲。リアルタイム約定には向かない。MPC の µs はリアルタイム向きだが、通信ラウンドと3ノードの可用性が前提。用途次第。
- **参加者が100社になったら** — MPC の集計は線形だが加算なのでほぼ無視できる。FHE は集計が線形に増え、按分が1社ごとに秒級なので、100社なら按分だけで数分〜十数分オーダー。
- **LLM の結論はモデル依存では** — その通り。Haiku 1種・プロンプト1通り・1実行。挙動の再現性は未検証で、確率的なばらつきがある。
- **能動的安全性(悪意ノード)** — 今回は準正直モデルまで。Shamir + 検証可能秘密分散や、FHE 側の計算の正当性証明は今後の課題。
- **ZK PoC はなぜ hash 比較じゃダメなのか** — hash 比較だと検証者に profile を見せて再計算してもらう必要があり、秘密を守るという目的と矛盾する。zkVM は秘密を明かさずに計算の正しさだけを示せる。
- **ZK PoC、証明にどれくらい時間がかかったか** — CPU ローカル証明で数十秒〜数分オーダー(guest 138157 cycles)。本番でリアルタイムに使うにはコストが高く、これも PoC の位置づけ。
