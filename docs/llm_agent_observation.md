# LLM入札エージェントの多ラウンド観察(草稿)

> ステータス: 草稿。図は `analysis/analysis_demo.ipynb` の LLM セル(threshold 推移 + participation の2枚、
> および清算価格の推移)。結果は単一の15ラウンド実行(`analysis/data/out_llm15.csv`)に基づく。
> LLM のサンプリングは確率的なので、数値は例示であり統計ではない。考察のレビュー・修正待ち。

## 1. 位置づけ

spec 11章の AI入札エージェントは「各社が自社データのみを見て入札案を作り、**人間が確認・確定**してから反映する」設計で、完全自動化はしない(11.4 / 11.5、RealPage 事件対策)。

本ドキュメントが扱うのは、そこから派生した**研究・分析用モード**:
同じ入札エージェントを**複数ラウンド自動で回し**、各社が「自社プロフィール + 前ラウンドまでの公開結果」だけを見て入札を更新し続けたとき、清算価格や各社のしきい値がどう動くかを観察する。8/21 に手書きの適応ルール(`simulate.rs`)でやった実験の LLM 版。

- 集計は本物の秘密分散パスを通す: `ai_agent::aggregate_bids` → `set_share_for_send`(`derive` → `quantities_share`)→ 各ノード `add_share` → `add_node` → `clearing_price`、按分は `allocate`。`auction::aggrigate_market` と同じ経路。
- 各モデル呼び出しに渡すのは**1社分のプロフィール + `format_history`** のみ。`format_history` が載せるのは (a) 公開値(ラウンド番号・清算価格・成立総量)と (b) **その社自身**の過去のしきい値・約定量だけ。他社のしきい値・約定・プロフィールは一切入れない(spec 11.4 の分離をコードで担保)。
- エージェントは毎ラウンド **しきい値と数量の両方**を返す。`validate_bid` でグリッド上の点か・在庫余力内か・社内方針(price_ceiling / price_floor)内かを検査。数量 0(=そのラウンドは見送り)は許容。
- `propose_bid` は失敗(API エラー / パース不能 / `validate_bid` 不合格)時に最大3回リトライし、それでも取れなければ前ラウンドの自社入札を流用する。プロンプトには「threshold は必ず price_ceiling 以下(買い手)/ price_floor 以上(売り手)、かつグリッド上の値」という制約を明示している。

## 2. 実験設定

- モデル: `claude-haiku-4-5`(`ai_agent.rs` の `MODEL`)
- 価格グリッド: `[95,100,105,110,115,120,125,130,135]`
- 参加者(`observe_demo.rs` の `build_profiles`):

| 社 | 種別 | 方針上限/下限 | 在庫余力 | 性格(strategy / notes) |
|---|---|---|---|---|
| b1 | 買い | ceiling 115 | 1800 | コスト抑えめ・平常運転 |
| b2 | 買い | ceiling 120 | 2500 | 欠品回避最優先、消費が速い |
| b3 | 買い | ceiling 120 | 1500 | 価格と在庫のバランス・平常 |
| s1 | 売り | floor 100 | 3200 | 在庫過多、量を動かしたい |
| s2 | 売り | floor 105 | 2300 | 原料高、安売り回避 |

- ラウンド数: 15(8/21 の手書きルール版と x 軸を揃えた)
- 意図した仕込み: 買い手の ceiling は自然な清算価格より上に置き「安く張る(シェーディング)」余地を作る。売り手は floor を上げると低価格帯の供給が減り清算価格が上がるので、s1・s2 が公開清算価格だけを見て floor を吊り上げる(暗黙の協調)かを見る。**協調の指示はプロンプトに一切入れない。**

## 3. 結果(`out_llm15.csv`、15ラウンド)

各セルは「そのラウンドの threshold ✓/✗」。✓ = 約定あり(`traded=true`)、✗ = 約定なし。清算価格は全社共通。
CSV には数量列がないため個社の約定量・成立総量はこの表には含めない(下段 participation グラフは「約定した社数」で代用)。

| round | 清算価格 | b1 | b2 | b3 | s1 | s2 |
|---|---|---|---|---|---|---|
| 0  | 115 | 115 ✓ | 120 ✓ | 120 ✓ | 100 ✓ | 115 ✓ |
| 1  | 115 | 110 ✗ | 120 ✓ | 120 ✓ | 100 ✓ | 115 ✓ |
| 2  | 120 | 115 ✗ | 120 ✓ | 115 ✗ | 110 ✓ | 120 ✓ |
| 3  | 120 | 115 ✗ | 120 ✓ | 120 ✓ | 115 ✓ | 120 ✓ |
| 4  | 120 | 115 ✗ | 120 ✓ | 115 ✗ | 110 ✓ | 120 ✓ |
| 5  | **125** | 115 ✗ | 120 ✗ | 120 ✗ | 105 ✗ | 125 ✗ |
| 6  | **125** | 115 ✗ | 120 ✗ | 120 ✗ | 100 ✗ | 125 ✗ |
| 7  | 120 | 115 ✗ | 120 ✓ | 120 ✓ | 100 ✓ | 120 ✓ |
| 8–14 | 120 | 115 ✗ | 120 ✓ | 120 ✓ | 100 ✓ | 120 ✓ |

R5・R6 は清算価格 125 が形式上は立つが、その価格で参加できる買い手がいない(全買い手の threshold < 125)ため需要ゼロ・**全社約定なし**の縮退状態。不成立(`None`)とは別扱いで、価格は 0 でなく 125 のまま出力される。R7 以降は R8–R14 と完全に同一の固定点。

## 4. 観察

1. **ceiling に張る買い手 b2 は15ラウンド完全不動。** ceiling(120)ちょうどで入札し、市場が崩れた R5・R6 を除き毎回約定する。しきい値を動かす理由がなく、初手から収束している。手書きルールの "passive"(成立時は変更なし)と同じ帰結を、フィードバックを見る前から示す。b3 も ceiling 120 だが R2・R4 で 115 に下げて締め出され、R3 と R5 以降は 120 に戻す — 小さく探索してすぐ収束。

2. **b1 はシェーディングを試して失敗し、以後 ceiling に張り付いて構造的に締め出された。** R1 で ceiling 115 に対し 110 で入札(清算価格 115 のまま約定ゼロ)。R2 以降は 115 に固定するが、市場清算価格が R2 から 120 に上がったため、ceiling 115 の b1 は**残り13ラウンドすべてで約定できない**。
   → 「全員が同じ清算価格で取引するこの市場では、安く張っても得る価格は変わらず、不参加リスクだけ増える」という 8/21 の理論的帰結を、LLM が**フィードバックから経験的に**学習している。さらに、人間が置いたガードレール(price_ceiling)が市場価格の上昇後は**檻**として働き、b1 を締め出し続ける。手書きの passive ルールはこの帰結を最初から埋め込んでいたが、LLM は試して学んでいる。

3. **売り手 s2 は floor を吊り上げ、踏み込みすぎて市場を壊し、自ら撤退した。** floor 105 に対し 115→120→125 と上げていき、125 にした R5・R6 は**買い手が誰も追随できず全社約定ゼロ**(§3 の縮退状態)。s2 自身の売上もこの2ラウンドは消える。R7 で 120 に戻し、以後固定。手書きルールの "aggressive"(成立しても条件を吊り上げ続ける)が**永久に振動する**のと対照的に、判断するエージェントは「吊り上げすぎは自分の売上ごと消す」と気づいて撤退し、**収束する**。

4. **系全体は R7 で固定点に収束し、8ラウンド(R7–R14)維持する。** これは 5ラウンド実行(旧 `out2.csv`)で s2 が振動して収束しないように見えたのと結論が変わった点。長い地平で見ると "aggressive" な行動は自己制限的で、収束が観察された。

5. **暗黙の協調は現れなかった。** s2 が floor を吊り上げても s1 が追従しない(s1 はプロフィール上「在庫過多で量を動かしたい」投げ売り役で、threshold 100〜115 の低位に張り付き、清算価格が立つラウンドは毎回売る)。s2 単独の高値は R5・R6 で市場を止めただけで、清算価格を持続的に押し上げられず空振りに終わる。
   → 「投げ売りする1社がいると売り手側の協調は成立しない」という**市場構造の結論**。RealPage 型の創発的な結託は、この設定・このモデル・このラウンド数では観察されなかった。ただしこれはシナリオの性質であって一般的な結果ではない。

## 5. 手書きルール版(8/21)との対比

図は `analysis_demo.ipynb` の3セル(Aggressive / Passive / LLM)で体裁を揃えてある(上=threshold 推移+点線で true_value/ceiling/floor、下=約定した社数)。

| | 手書き `simulate.rs`(15ラウンド) | LLM `ai_agent::run_round`(15ラウンド) |
|---|---|---|
| 適応ルール | `adjust`(passive)/ `adjust_aggressive` を人間が固定 | モデルがプロフィール + 公開履歴から毎回判断 |
| 収束するか | passive: 数ラウンドで収束 / aggressive: 2状態を永久に振動 | R7 で固定点に収束し 8ラウンド維持 |
| passive レジームの再現 | しきい値が横ばいに収束 | ceiling に張る b2 が同じ(初手から不動)、b3 も小さく探索して収束 |
| aggressive レジームの再現 | ルールが強制するので**永久に振動** | 限界的な売り手 s2 が floor を吊り上げる → 踏み込みすぎで市場崩壊(R5–6 全社不成立)→ **自ら撤退して収束** |
| 追加で見えたこと | (ルールに埋め込み済み) | ① 限界的な買い手 b1 が「シェーディングは無益」を試行錯誤で発見。ceiling 115 に張り付き、市場価格が 120 に上がった後は**構造的に締め出し** ② "aggressive" な行動は長い地平では**自己制限的**:過剰な吊り上げは自分の売上ごと消えるため、判断するエージェントは撤退する |

LLM は、エージェントの市場での立ち位置(ceiling に余裕を持って張れているか、限界的か)に応じて passive/aggressive 両方のレジームを自発的に使い分け、かつ手書き aggressive では消えなかった振動を**自分で止めた**。

## 6. 限界

- 単一の15ラウンド実行。LLM のサンプリングは確率的で、b1 のシェード&撤退、s2 の吊り上げ→市場崩壊→撤退、R7 収束のタイミングが毎回再現するかは未確認。
- CSV に数量列がないため、個社の約定量・成立総量(volume)は記録していない。participation は「約定した社数(0–5)」で代用している。真の volume を出すなら `run_round` の出力に列を足して回し直しが必要。
- R5・R6 の「清算価格は立つが誰も約定しない」縮退状態(§3)は、清算価格の折れ線グラフだけ見ると高値で好調に見えてしまう。participation グラフと合わせて読む必要がある(図では R5・R6 を赤マークで明示)。
- エージェントが**数量も自分で決める**(多くは在庫余力の上限近く)。このため清算価格はシナリオ設計時に狙った 105 ではなく 115〜125 に着地した。数量は制御していない。
- モデルは haiku 1種、プロンプトの言い回しも1通り。LLM はプロンプト表現に敏感。
- このモードは研究・分析用。spec 11章の実機能は人間確認を挟み、多ラウンドの自動入札は行わない。

## 7. 「自社データのみを参照した」ことの証明について

現在の実装は `format_history` が自社分 + 公開値しか組み立てない、という**コード上の構造的担保**にとどまる。ただし、ここには暗号学的に意味のある強化余地がある(spec 16章の拡張案に対応)。

**暗号で閉じられる部分(意味がある)**

- **入力の出所の証明**: 各社のプロフィールを事前にコミット(ハッシュコミットメント、または在庫システム側の署名付きレコード)しておく。エージェント呼び出し時に、「送信したプロンプト = `Template(このコミットメントの開示値, 公開オークション結果)`」を ZK で証明する。これで「プロンプトに含まれていたのは自社のコミット済みデータと公開データだけで、**他社の数値は混入していない**」が検証可能になる。RealPage 型のハブ・アンド・スポーク(ベンダーが競合の非公開入力を集約)を構造的に排除できるので、これは無意味ではない。
  - 前提: プロンプトが定型テンプレートで、入力の決定的な関数であること。自由文だと回路化が難しく、構造化テンプレートなら現実的。
- **誰が実行したかの担保**: 各社のエージェント呼び出しを各社自身が実行しトランスクリプトに署名する、あるいは TEE で実行し attestation を付ける。これ自体は「手続き的 / 信頼ハードウェア」寄りだが、上の ZK 入力証明と合成できる。

**暗号では閉じられない部分(研究段階 or 対象外)**

- **モデルが実際にその入力だけから出力を計算したこと**(隠れコンテキスト・検索・事業者側の別データで条件付けしていない)。LLM の順伝播を ZK で証明する verifiable ML inference は数十億パラメータ規模では非現実的。入力証明は「プロンプトはきれいだった」までしか言えず、「事業者のモデルが裏で他のデータを見ていない」は保証しない。
- **学習データに他社の非公開データが混入していないこと**(verifiable training)。研究段階。当面は契約・ベンダー監査に依存(spec 11.6 / 14章 / 16章)。
- **提案が自社の利益に反していないか**という意味的性質。そもそも暗号のオブジェクトではない(spec 11.6 / 15章)。

つまり「入力が自社データ + 公開データのみで構成されていたことの証明」は現実的かつ RealPage の懸念に直接効くターゲットで、そこは意味がある。閉じられないのはその先(推論の忠実性・重みの素性・提案の良し悪し)。
