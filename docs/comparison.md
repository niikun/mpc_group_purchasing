# MPC と FHE の比較(草稿)

> ステータス: 草稿。定量値のうち FHE 側はベンチハーネス(`fhe-rust/examples/derive.rs` の `main`)の出力で差し替える。
> 定性の記述はユーザーのレビュー・修正待ち。

## 1. 何を比較しているか

同一のダブルオークションのロジックを、2つの技術で実装した:

| 段階 | 処理 | MPC 実装 | FHE 実装 |
|---|---|---|---|
| derive | 価格帯ごとの参加判定(買い手 `price ≤ threshold` / 売り手 `price ≥ threshold`) | `auction::derive`(平文、各社の手元) | `fhe_derive`(暗号のまま、9価格帯すべてを `FheBool` + cmux で分岐なし評価) |
| 集計 | 需要曲線 D(p) / 供給曲線 S(p) の構築 | `quantities_share` で加法的3分割 → 各ノード `add_share` → `add_node` で復元 | `fhe_aggregate`(暗号9ベクトルを要素ごとに準同型加算) |
| 清算価格 | `D(p) ≤ S(p)` を満たす最低価格 | `clearing_price`(復元後の平文をループ、最初に成立で `break`) | `fhe_clearing_price`(9バンド全評価 + 「見つけた」フラグのラッチ、分岐なし) |
| 按分 | `traded × desired / total` | `allocate`(整数除算、各社の手元) | `fhe_allocate`(`FheUint32` に拡張、暗号 × 暗号の乗算 + 暗号 ÷ 暗号の除算、cmux でゼロ除算ガード) |

入力(各社の threshold・quantity)は両方式とも最後まで非公開。公開されるのは D(p)/S(p)・清算価格・成立総量、および各社に個別開示される按分結果。

固定シナリオ(両ベンチ共通、`auction.rs::test_aggrigate_market3` と同じ): 買い手3社 `(th,q) = (110,200) (120,100) (95,100)`、売り手2社 `(110,200) (100,200)`。期待清算価格 110、約定 `(200,100,0,150,150)`。

## 2. 定性比較

| 軸 | MPC(加法的秘密分散、3ノード) | FHE(tfhe-rs、単一評価者) |
|---|---|---|
| **信頼の起点** | 準正直・3-of-3 加法分散。**3ノード全員が結託しない限り**入力は秘匿(1ノードでも正直なら安全)。しきい値 k-of-n(Shamir)は未実装。悪意あるノードの改ざんに対する保証はない(能動的安全性なし) | 復号鍵 `client_key` を持つ者は**すべて復号できる**。計算は `server_key`(公開評価鍵)を持つ単一の評価者が実行。本実装では鍵配布を第1段階の3ノード分散と同様に簡略化(= 未解決)。Zama 本来の答えである しきい値復号 KMS(13ノード)は使っていない |
| **早期終了** | できる。清算価格探索は平文に復元してからループするので、最初に `D(p) ≤ S(p)` になった時点で `break` | **できない**。暗号値で分岐できないため、9価格帯すべてを必ず評価(各バンドで比較 + ラッチ更新 + cmux 2回)。構造的な差 |
| **コストの出方** | ノード間の**通信ラウンド**。演算そのもの(法 M 上の加算)はほぼゼロ。レイテンシ ≈ f(ネットワーク往復, ラウンド数, ノード数)。実プロセス版では TCP + tokio | **単一マシンの計算時間**。計算中の当事者間通信はゼロ。準同型演算そのものが重い(16bit 比較・cmux は ms 級、32bit 除算は秒級)。レイテンシ ≈ f(回路サイズ, ビット幅, コア数) |
| **参加者数に対するスケール** | 集計はシェアの要素ごと加算 = O(参加者 × 9) の法加算 ≈ 無料。支配項は固定のラウンド構造のまま | 集計は O(参加者) の準同型 derive + 加算で線形かつ非ゼロ。按分は O(参加者) の除算で1回あたり秒級。参加者数の増加に弱い |
| **オンチェーン性** | 本質的にオフチェーンのプロトコル | 本実装はオフチェーン。fhEVM(オンチェーン検証 + Zama KMS)への道はあったが、残り期間で2言語を新規学習するコストと引き換えに採用せず |
| **出力の完全性 / 監査可能性** | ノードが正直に集計したことの検証はない(準正直モデル) | 単一評価者が誤った回路を評価しても検出できない。証明は伴わない |
| **実装で当たった壁(学習曲線の質)** | 秘密分散の代数(法 M 上の `Fp`)、3ノードのオーケストレーション、非同期(tokio/mpsc → TCP)、シリアライズ、poisoning とロバスト性。= **分散システムの難しさ** | 秘密分散なし・多者オーケストレーションなし。代わりに: ビット幅の予算管理(u16 vs u32、オーバーフロー)、データ依存の分岐をすべて cmux に置換、`FheBool` は平文 `bool` にできない、Copy 不可な暗号文の取り回し、鍵のライフサイクル。= **回路設計の難しさ** |

## 3. 定量比較(1取引 = 買い手3社 + 売り手2社)

計測条件: `--release`。FHE は `RUSTFLAGS="-C target-cpu=native"`。MPC は1000回ループの中央値、FHE は5回・先頭破棄で残り4回の中央値。
マシン: Intel Core i7-10850H(6コア/12スレッド、2.70 GHz)、WSL2。`std::thread::available_parallelism()` = 12。tfhe-rs は内部で rayon マルチスレッド、下記はこのマシンでのウォールクロック時間。

| フェーズ | MPC | FHE |
|---|---|---|
| 鍵生成(1回のみ、区間外) | — | 818 ms |
| 入力暗号化(10値、区間外) | — | 5.1 ms(≈0.5 ms/値) |
| 集計 D(p)/S(p) 構築(`fhe_derive` 込み) | (通しに含む) | median **16.6 s**(min 15.8 / max 16.7) |
| 清算価格スキャン(9バンド) | (通しに含む) | median **12.6 s**(min 11.6 / max 12.8) |
| 按分 ×5社 | (通しに含む) | median **75.8 s**(≈15.2 s/社、min 72.3 / max 76.0) |
| **1取引 通し** | median **1.2 µs**(min 1.1 / max 1.5、n=1000) | median **105.0 s**(min 99.7 / max 105.1、n=4) |

**比 ≈ 105 s / 1.2 µs ≈ 8.8 × 10⁷ 倍(約8桁、およそ9千万倍)。** 有効数字2桁で十分で、FHE 側の小数点を詰める意味は薄い。

フェーズの内訳(FHE、通しに占める割合): 按分 72%、集計 16%、清算スキャン 12%。**暗号 ÷ 暗号の除算を含む按分が支配項**。集計は参加者数にほぼ線形(3社 9.4s ≈ 3.1 s/社 → 5社 16.6s ≈ 3.3 s/社)、清算スキャンは価格グリッド段数で決まる固定費。

正しさの確認: FHE パイプラインの清算価格は復号すると 110 で MPC(`aggrigate_market`)と一致。ただし `fhe_allocate` の生出力は `[200, 100, 100, 150, 150]` で、b3(threshold=95、清算価格110では不参加)が 0 でなく 100 になる。MPC の `aggrigate_market` が行う参加ゲートを FHE 側で未実装なため(セクション5-4)。

## 4. 考察(軸ごと)

_(ユーザーのレビュー・修正待ち。以下は草稿)_

### 4.1 なぜ MPC はほぼ無料(1.2 µs)なのか

このダブルオークションが必要とする演算は**加算と比較だけ**で、乗算・除算は按分にしか現れない。加法的秘密分散では:

- 加算 = 各ノードがシェアを局所的に足すだけ(法 M 上の `u64` 加算)。D(p)/S(p) の構築は数十回の加算で終わる。
- 清算価格の比較 = シェアを復元して**平文**で行う。比較そのものに暗号的コストはない。
- 按分の乗除も復元後の平文整数演算。

つまり「重い処理」が原理的に存在しない。1取引が µs で終わるのはこのため。**このベンチにはノード間通信が含まれていない**点に注意(§5-5): 実プロセス版では TCP + tokio のラウンドが乗るので、実運用のレイテンシはネットワーク往復回数で決まる。

### 4.2 なぜ FHE は分オーダー(105 s)なのか

同じ加算・比較を**暗号文のまま**行うと桁が変わる:

- 準同型加算は比較的軽いが、`fhe_derive` の参加判定に必要な `FheBool` 比較 + cmux が価格帯ごとに走り、集計フェーズで 16.6 s。
- 清算スキャンは**早期終了できない**ため 9 バンドすべてで「比較 + ラッチ更新 + cmux ×2」を評価する固定費で 12.6 s。
- 按分は `FheUint32` に拡張した上での**暗号 × 暗号の乗算 + 暗号 ÷ 暗号の除算**。除算は tfhe-rs で最も重い演算の一つで、1社あたり ≈15 s、5社で 75.8 s と**通しの 72%** を占める。

演算コストの階層(このマシン): 16bit の準同型加算 ≈ ms、16bit 比較・cmux ≈ 10–100 ms、32bit 乗除 ≈ 秒。回路が「何ビット幅で・どの演算を・何回」使うかがそのまま実行時間になる。

### 4.3 スケール特性

- **MPC**: 参加者が増えてもシェアの局所加算が増えるだけ(≈無料)。支配項は固定のラウンド構造。
- **FHE**: 集計は参加者数にほぼ線形(≈3.3 s/社)、按分は参加者ごとに除算1回(≈15 s/社)。**参加者数に対して線形に悪化**する。価格グリッドの段数を増やすと清算スキャンと derive がその分伸びる。

### 4.4 トレードオフの非対称性

同じ「隠したまま計算する」を実現しても、支払う通貨が違う:

| | 主なコスト | 主な信頼の前提 |
|---|---|---|
| MPC | 当事者間の**通信ラウンド**(往復回数 × ネットワーク遅延) | ノードが**結託しない**(3-of-3、1ノードでも正直なら秘匿) |
| FHE | 単一マシンの**計算時間**(回路サイズ × ビット幅) | `client_key` 保持者が**単一の復号点**(しきい値復号は未導入) |

MPC は「みんなで少しずつ持つ代わりに何度もやり取りする」、FHE は「一人が全部やる代わりに一回一回が重い」。

### 4.5 どちらを選ぶか(この題材で)

当事者が少数(数社)で相互に接続でき、準正直・非結託の前提を許容できるなら **MPC が実務的に優位**(µs、round さえ許せば十分速い)。当事者間の同期通信を排したい・提出を非同期にしたい・将来オンチェーン化(fhEVM)の芽を残したいなら FHE に意味が出るが、本題材(少数の事業者、1回の清算、加算主体の回路)では 8 桁のコスト差を正当化する要件はない。FHE の価値は「単一サーバに預けて誰とも通信せず処理させられる」という**運用形態**にあって、生の速度ではない。

## 5. 制限事項(spec 15章へ反映)

1. **鍵管理の簡略化** — MPC は 3-of-3 加法分散(しきい値 k-of-n 未実装)。FHE は `client_key` を単一主体が保持する前提で、しきい値復号 KMS を使っていない。どちらも「復号権限の分散」は本質的に未解決。
2. **能動的安全性なし** — MPC ノード・FHE 評価者が正しく計算したことの検証(ZK 等)は行っていない。準正直モデル。
3. **オンチェーン性なし** — 決済・検証をチェーン上で行う実装はしていない。fhEVM 版は採用を見送った。
4. **FHE 按分の参加ゲート未実装** — `fhe_allocate` は `traded × desired / total` を計算するだけで、MPC の `aggrigate_market` が行う「清算価格で参加していない社を除外する」ゲート(`price ≤ threshold` 等)を暗号側で適用していない。ベンチのサニティ出力で確認済み: b3(threshold=95)は清算価格110では不参加なのに生出力が 100(本来 0)。実装するには「清算価格 vs threshold」の `FheBool` 比較と cmux が各社1回ずつ追加で必要(≈ さらに数十秒/取引)。
5. **計測はマシン依存** — FHE の数値は1台のマルチコア機のウォールクロック。ノード分散配置での MPC 通信遅延は本比較には含まれない。

## 6. この比較が主張しないこと

- どちらの技術が「優れている」か、という一般論。題材(少数当事者・単一清算・加算主体の回路)に強く依存した結果である。
- FHE の絶対性能。ビット幅の削減、演算の並列化、鍵・暗号文のシリアライズによる償却などの最適化はしていない。
- 能動的攻撃者・ネットワーク分断・鍵漏洩といった脅威下での安全性。
